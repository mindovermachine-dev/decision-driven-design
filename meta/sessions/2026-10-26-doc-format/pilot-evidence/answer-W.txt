1. What each tool's responses must declare for this task

The document says every response (not every tool) must declare four things. These are ground relation, resolution, boundedness and verdict. An uncontrolled response must also carry observed-at and a revalidation method. The default is to revalidate on every call.

- read_file
  - Ground: I would declare it uncontrolled. The agent can change the same files with write_file during the run, so an earlier read can go stale. It needs observed-at plus a cheap validator, such as mtime or a content hash.
  - Resolution: unresolved. It hands over file content, for example the manifest. It should say what is still undecided, such as "locating the fastjson dependency entry and its current version constraint".
  - Boundedness: it must state its bound, such as a maximum number of bytes or lines. If it cannot bound its output, it must say "unbounded".
  - Verdict: none.
- list_dir
  - Ground: uncontrolled, for the same reason as read_file. Observed-at plus a validator, such as the directory's mtime or a hash of the listing.
  - Resolution: resolved for "which entries exist in this directory". It does not resolve which of those files is the manifest or the lockfile. That stays open, and the response should say so.
  - Boundedness: the entry count, or "unbounded" for very large directories.
  - Verdict: none.
- fetch_url (registry index page for fastjson)
  - Ground: clearly uncontrolled, because the registry belongs to someone else. Observed-at plus revalidation through a validator such as an ETag or Last-Modified header, not a TTL.
  - Resolution: unresolved. It returns a page for the agent to interpret. Still to be decided: which versions exist, which is the latest, and which is compatible with this project. The registry does not decide compatibility.
  - Boundedness: the page size, or "unbounded". An index page could be large.
  - Verdict: none.
- run_tests
  - Verdict: yes. It is the only verifier in the set.
    - What it checked: the behaviour the test suite covers, against the workspace as it was when the tests ran.
    - What it did not check: code paths the tests do not cover, conventions and structure, whether the version chosen is actually the latest compatible one, and lockfile or transitive-dependency consistency if the tests do not exercise those.
  - Ground: the result is a reading of the workspace at run time, so it is uncontrolled. Observed-at plus a hash of the workspace, so the harness can tell that a later write_file has made the result stale.
  - Resolution: resolved for pass/fail. Unresolved for interpreting failure output: which failure is caused by the bump, and what to change.
  - Boundedness: the log output should be bounded (truncated with a stated limit), or declared unbounded.
- write_file
  - Ground: the write itself creates the ground, so I would declare its confirmation as controlled. It should report the resulting hash or mtime, so later reads and test results can be checked against it.
  - Resolution: resolved, in the sense that "file X now has content Y".
  - Boundedness: bounded (a confirmation only).
  - Verdict: none. See section 4, because the document does not really cover write tools.

2. Binding a toolset

Step 1 is to enumerate the governing decisions. My list is below. The document also wants an assurance level, which I was not given (see section 4).

- D1: Which file or files declare fastjson, and what version they currently pin.
- D2: Which versions of fastjson exist, and which one is the latest.
- D3: Which of those versions is compatible with this project (runtime version, other dependencies, API changes).
- D4: Which files must be edited (manifest, lockfile, and code if the API changed).
- D5: The edits themselves.
- D6: The tests pass after the change.
- D7: Nothing outside the test suite's coverage broke (conventions, untested paths, transitive dependency conflicts).
- D8: The registry reading used for D2 and D3 is still current when the change is written.

Step 2 is to bind all five tools: read_file, list_dir, fetch_url, run_tests and write_file. Then, from the declarations above:

| Status | Decisions | Why |
|---|---|---|
| Resolved by a tool | D5 and part of D1 | write_file resolves the edits. list_dir resolves which files exist, but not which one is the manifest. |
| Verified by a verdict | D6, and part of D3 | run_tests verifies the tests pass. It covers compatibility only as far as the tests reach. |
| Partly checkable | D8 | fetch_url's validator (ETag) lets the agent revalidate the registry reading before writing. The harness should treat the reading as unpinned if it has lapsed. |
| Open (the escape set) | D1, D2, D3, D4, D7 | See below. |

Why each open decision stays open:
- D1: the agent has to interpret the manifest.
- D2: the agent has to interpret the registry page to find the latest version.
- D3: compatibility beyond what the tests exercise.
- D4: no tool tells the agent which files a bump requires.
- D7: nothing checks it.

Step 3 is to freeze the binding for the run.

Two further gaps:
- There is no tool to install or resolve dependencies. Whether run_tests actually uses the new version depends on how the test runner works.
- That makes the D6 verdict weaker than it looks, so I would note it as an assumption.

3. If the agent finds mid-run that it needs a capability I did not bind

An example would be a package-manager install command or a shell. The agent must:
- declare "this task requires a capability I was not given";
- stop the run;
- route the decision to a human.

It must not improvise with the tools it has. For example, it must not write a script into the workspace and get it run through run_tests to gain shell access. The harness also must not add the tool during the run, because the binding is frozen and dynamic loading is excluded. A human then decides, and the task is bound again and re-run. The document says this refusal path must exist. Without it, the escape reappears looking like a successful run.

4. Points where I was unsure

- Whether workspace files are "controlled" or "uncontrolled".
  - The fetch example (local file vs remote URL) suggests local files count as different ground, maybe controlled.
  - The revalidation section (re-stat, mtime, hash for local tools) suggests local reads are uncontrolled readings.
  - I chose uncontrolled because the agent writes to the same files.
- Write tools. Section 2 is written for tools that read or check. It does not say what a write tool's response should declare.
- "Declared assurance level". The harness is told to enumerate decisions "at its declared assurance level". The document does not say what assurance levels are, or who sets one for this task.
- Who enumerates the governing decision set, and how. My list in section 2 is my own guess.
- What counts as "resolved". Under the document's definition (decided authoritatively before the actor sees anything), almost nothing in this toolset resolves the task's real decisions. I was unsure whether that is the intended outcome, or whether I misapplied the term.
- The undefined vocabulary. I could not use these terms with confidence:
  - floor, escape, the formula `escape = open_residual × p_err(load)`, and load;
  - judgment store and encoded store;
  - the admission test, tolerance and seam demand;
  - WorkUnit and frozen bundle, and RFC 0005.
- "Class". The document says the harness computes a tool's class by combining its declarations with the task. It refers to another document (tool-surfaces.md §3) for the classes and how to compute them. I did not have that document, so I computed no class.
- What the harness should do with a lapsed response in practice. "Treat dependent decisions as unpinned" is clear in principle. I could not tell whether that should block the write, warn, or fail the run.
- Whether stopping on a missing capability counts as a task failure, and what form the "elicitation" route to a human should take.
- Whether run_tests' ground should be declared in terms of the workspace snapshot. Also whether its verdict covers anything about compatibility at all, given there is no install step.
- The document marks itself as "proposed", and its location is undecided (apparatus vs applications). I was unsure how binding it is.
